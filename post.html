跟随平滑延迟

一个十万粒子的 Canvas 页面里，摄像头已经检测到手掌，粒子也在不停旋转、张合、变换形态。可用户的一句话点出了问题所在：「手动，粒子也动，但它不跟着我走。」

这不是渲染故障，而是一次典型的能力错觉：系统有响应，却缺少用户真正期待的那一层映射。本文复盘这次修复从诊断到落地的完整过程。

一、症状：动，但不跟随

用户的描述很克制——「手势动，粒子也动，鼠标动也是」。三种输入都能让画面产生变化，但变化的方向与输入之间没有任何空间对应关系。

拆解后得到三条可验证的现象：

  • 开启摄像头后，状态栏正确显示「检测到 1 只手」，说明手部 landmark 数据已经进来。
  • 张开与握拳能明显改变粒子的扩散半径，说明张合度映射是通的。
  • 手掌左右移动时，粒子群整体纹丝不动；鼠标移动只产生局部涡流，并不带动粒子群位移。

结论指向一个明确判断：问题不在"有没有动"，而在"动的是不是我期待的自由度"。

二、诊断：从代码出发，而不是从猜测出发

面对一个 575 行的单文件页面，直接改是想当然的。先把源码拉下来通读，定位手势链路的三个关键位置。

第一处，手势回调。MediaPipe 的 onResults 拿到 multiHandLandmarks 后，只做了一件事：用 handOpen() 计算手掌张开程度，写入 targetOpen。landmark 里完整的 x / y 空间坐标，在这一步被整体丢弃。

第二处，主循环。targetOpen 被平滑成 smoothOpen，再换算成 scale（缩放）与 turb（湍流）。也就是说，手势唯一的输出通道是"张合"，没有任何平移或旋转自由度。

第三处，鼠标链路。鼠标确实记录了 mouseX / mouseY，但只用于两个局部效果：半径约 161 像素内的切向涡流，以及 0 号蝴蝶的追随。粒子群的重心始终钉在屏幕中心。

一个页面同时打开了"自动巡演"：每 7 秒切换一次形态，粒子持续自转。这层自主运动盖过了微弱的交互反馈，让"不跟随"的体感进一步放大。

三、根因：缺失的"位置层"

把整条链路画出来，缺口一目了然。

输入层有手掌坐标与鼠标坐标；计算层有张合度、缩放、湍流、涡流；渲染层有逐粒子的三维投影。但从"位置输入"到"整体位移"之间没有任何一条边。

  • 手势链路：landmark → 张合度 → scale / turb → 粒子形态变化
  • 鼠标链路：指针坐标 → 局部涡流 / 单只蝴蝶 → 局部扰动
  • 缺失链路：位置输入 → 平滑偏移 → 投影坐标整体平移

用户的心智模型是"手到哪，粒子跟到哪"，而代码实现的是"手张多大，粒子散多开"。两者对"跟随"的定义根本不同。

四、方案：三层改动，一次提交

修复遵循最小改动原则，只补上缺失的那一层，不重写粒子算法、不触碰形态生成、不改变渲染管线。

第一层 · 状态。 新增手掌归一化坐标 handNX / handNY 与一组屏幕空间偏移量 followX / followY、followTX / followTY，分别保存平滑值与目标值。

第二层 · 采集。 在 onResults 中取 landmark 9（中指根部，接近手掌中心）作为位置源。由于摄像头画面做了镜像显示，横坐标取 1 - palm.x，让粒子的运动方向与用户在预览里看到的手势一致；纵坐标直接映射。

第三层 · 应用。 主循环里按优先级计算目标偏移：手势有效时用手掌位置，否则用鼠标位置，两者都没有则平滑回中。随后把偏移量加到每个粒子的投影结果上。

输入源判定条件目标偏移
手掌摄像头开启、检测到手、900ms 内有更新归一化位置映射到画面的 62%
鼠标指针位于画布内相对中心的位移取 55%
无输入以上都不成立平滑回中
 
const handLive = camActive && handFollow && (performance.now() - lastHand < 900);
if (handLive) {
  followTX = (handNX - .5) * W * .62;
  followTY = (handNY - .5) * H * .62;
} else if (mouseX > -900) {
  followTX = (mouseX - hw) * .55;
  followTY = (mouseY - hh) * .55;
} else {
  followTX = 0; followTY = 0;
}
followX += (followTX - followX) * .10 * step;
followY += (followTY - followY) * .10 * step;

五、实现细节：三个容易踩的坑

镜像方向。 摄像头原始画面与 CSS 镜像后的预览方向相反。若直接用 palm.x，用户向左挥手、粒子却向右跑，体感会比不跟随更糟。取反是必要的一步。

时间窗口。 手势检测是异步回调，帧率低于渲染循环。用 900ms 的"新鲜度"窗口判断手势是否有效，手移出画面后能迅速把控制权交还给鼠标，避免粒子卡在最后位置。

平滑系数。 0.10 的阻尼让位移有约十帧的跟随延迟。这个值在"跟手"和"不抖"之间取平衡：再高会放大 landmark 抖动，再低会显得迟钝。

六、结果与边界

改动落地后，手掌左右、上下移动会带动整个粒子群平移；鼠标在画布内移动时同样生效，原有的涡流与蝴蝶追随保留。自动巡演默认关闭，避免自主运动掩盖跟随反馈。

需要说明的边界：

  • 位置跟随作用于屏幕空间的投影结果，不改变粒子之间的相对结构，形态本身仍然完整。
  • 手势位置取自单只手掌（列表中的第一只），多手场景下张合度仍取平均值。
  • 摄像头权限被拒绝或 MediaPipe 模型加载失败时，自动降级为鼠标跟随，页面其余功能不受影响。

七、结语

这次修复的技术量不大——真正新增的核心逻辑只有十余行。但它说明了一个容易被忽略的事实：交互故障未必是功能失效，也可能是能力映射的错位。

当系统"有响应"却让人觉得"没反应"时，与其继续加大响应幅度，不如回到输入与输出之间，检查那条最直觉的映射是否真的存在。
